## 0. 一页结论

**组织方式**：按六个目标（质量、效率、稳定性、不随意变更范围、不随意重构、少返工）各自的失效原因安排工作，分四层落实：任务合同、执行中护栏、可信交付门、度量与审查。

**三条原则**：

1. **先启用，再开发。** 现有机制没用足的先用足。
2. **先记录，再拦截。** 会拒绝 Worker 的约束，没有开发集的误拦数据不进入正式对照和日常启用。
3. **止损只管钱，不管目标。** 基线探查可以停止付费扩样，不能把产品目标判为「不需要」。

**当前状态**：六项目标都还没有当前候选版本的真实端到端验收。遗留系统和大任务的无关重构改善均为**待交付**，两个场景分别验收，任一场景证据不足，这一必达项就没有完成。

## 2. 总体设计：四层

```text
第一层 任务合同      写清楚要什么、能改哪里、什么不许动
        ↓
第二层 执行中护栏    越界即拒；改动量及时反馈给 Worker
        ↓
第三层 可信交付门    检查真的跑了、结果真的属于这次代码；异常可恢复
        ↓
第四层 度量与审查    按原始需求出指标；审查退回能精确到某一处改动
```

| 层 | 主要服务的目标 | 现有能力 | v5.1 的工作 | 性质 |
| --- | --- | --- | --- | --- |
| 一、任务合同 | 范围、重构、返工、质量 | 任务卡 v3、`lint-task`、硬预算、`outOfScope` | 书写标准；合同自洽提示；大任务拆卡规则 | 零开发为主；一条 lint 提示已实现 |
| 二、执行中护栏 | 范围、重构、效率 | 路径守卫、计划比对、受保护资产 | 检查后反馈增量改动；计划宽度记录 | 小改动，只提示不拦截 |
| 三、可信交付门 | 质量、稳定性 | 证据核验、先红后绿、恢复命令 | 强绑定默认开启、隔离、操作者通道（即 C1） | 条件见附录 A |
| 四、度量与审查 | 全部六项 | 决策日志、`hephi stats`、`hephi summary`、盲评工具链、SA 的行内评审入口 | 指标口径；真实审查退回试验；逐块归属声明（试验） | 指标零开发；其余需开发集试验 |

不做的事（最小化约束）：不加审查 Agent，不解析语言语法，不判断格式化或重命名，不新建执行模式，不让插件判断改动是否合理。

## 3. 第一层：任务合同标准

**依据**：范围和重构的授权边界只能由需求方给出；开发集出现了测试路径与写权限不一致且未 ready 的候选案例，须先消除确需写测试时的合同矛盾。
**适用范围**：无关重构专项的任务。Q1 的任务卡按其冻结清单，不动。

### 3.1 书写标准

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| 版本与类型 | 统一 v3。修复和新功能用 `code`；获授权的结构改造单独开 `refactor` 卡 | 在入口区分授权的重构和顺手重构 |
| `acceptance[].paths` | 精确文件，只列这条验收项**需要新增或修改**的文件 | 路径就是写权限，不多给 |
| `acceptance[].tests` | `code` 卡必填，指明证明该验收项的测试 | 见下方「测试文件的两种情况」 |
| `outOfScope` | 遗留系统必填两类：必须保留的对外行为；不得改动的模块、类或函数。写具体名字 | 每轮都出现在 Worker 的系统提示里 |
| 规模预估 | 每张卡记录预估的改动文件数和行数，写在任务元数据里，**不写进 `budget`** | 只用于观察，见 3.2 |
| `budget`（硬边界） | 只有负责人或需求方明确批准「超出即拒绝」时才填写 | 填了就会拒绝，见 3.2 |
| 受保护资产授权 | 需要修改已有的受保护测试时，在对应验收项写 `authorizes` | 否则合法的测试同步会被拒 |

**测试文件的两种情况**：

- **需要 Worker 新写或修改测试**：测试文件必须同时列入该验收项的 `paths`，否则合法编辑会被范围守卫拒绝；需要修改受保护测试时还须有对应授权。
- **测试已经存在且在基线上就失败**：测试只作为验收依据，不需要写权限，不要列入 `paths`。源码确认这种写法合法：红色运行可以直接在基线提交上完成（evidence-verifier.ts L438-459）。

`hephi lint-task` 的 `focus.tests-outside-paths` 是提示而不是报错，原因就是第二种情况合法。投递前由任务作者判断属于哪一种。

### 3.2 预算：硬边界和规模预估分开

源码行为（discipline.ts L214-250）：任务卡没填 `budget` 时，默认的 8 个文件、400 行只记录不拒绝；一旦填了 `budget`，超限就拒绝。

所以「给每张卡填预估量 2 到 3 倍的预算」等于在没有误拦数据时就启用了硬限制，与「先记录，再拦截」冲突。v5.1 改为：

| | 规模预估 | 硬边界 |
| --- | --- | --- |
| 写在哪里 | 任务元数据（评估任务的 `task.json`），不进任务卡 | 任务卡 `budget` |
| 超出时 | 不拒绝；指标脚本报告「实际改动量 ÷ 预估」 | 拒绝 |
| 谁决定 | 任务作者 | 负责人或需求方逐卡批准 |
| 什么时候用 | 所有专项任务 | 开发集试验中专门测试；通过误拦门槛后才进入正式对照的实验组 |

### 3.3 大任务拆卡

- 一张卡只对应一个里程碑；跨模块依赖按「先接口、后调用点」排成多张卡。
- 拆分由需求方或 Lead 完成，插件不参与。
- **拆卡不改变验收单位**：大任务的结果按原始需求（父任务）最终合并的整份改动来评，见 §6.2。

**子卡的串联与合成**（v5.2 新增；主结果取样前全程无人工介入）：

- 拆卡方案（子卡数、依赖和执行顺序）随任务卡在开跑前冻结并记哈希，运行中不调整。
- 有依赖的子卡串行执行：后序子卡的 `baseSha` 取前序子卡 ready 时的 HEAD。前序子卡未 ready，后序不启动，父任务按实际终态记录。
- 互不依赖的子卡可以从同一个前序 HEAD 并行出发，由脚本按冻结的顺序机械合并，不做任何手工编辑。
- 合并冲突、或合成 HEAD 上的整体验收失败：父任务记为 failed 或 blocked，照常计入 N 和成本。Lead 或人工在取样前解决冲突属于人工介入，不允许；取样之后的修复另列，不进主结果。
- **已核对的部分**：插件层面，合同的 `baseSha` 取自环境变量 `HEPHI_BASE_COMMIT`（`activation.ts:632`），检查和 ready 都以它为基线，所以机制上允许后序子卡换基线。
- **待验证（B2 的通过条件）**：用一个大任务跑通以下三点，缺一即判未跑通，实验组的大任务不拆卡，§6.6「拆卡」一行填「无」：
  1. 派工方能把后序子卡的 `HEPHI_BASE_COMMIT` 设为前序子卡 ready 时的 HEAD，合同回读的 `baseSha` 与之相等；
  2. 后序子卡的工作区里存在该提交，红色运行和 ready 核验都正常完成；
  3. 脚本合成的 HEAD 上，整体验收和隐藏参考验收测试都能运行并留下记录。

## 6. 第四层：度量与审查

### 6.1 计数单位：原始需求（父任务）

所有专项指标按**原始需求**计数，不按任务卡或工单计数。

- 一个原始需求可能对应一张卡，也可能拆成多张卡，还可能有重投。它们都归到同一个父任务。
- 纳入集合是开跑前分配的**全部父任务**，包括失败、阻塞、放弃、未启动和重投；重投保留原 `parent_id`。各指标分母按 §6.2 明示，缺最终 diff 不能算作无关改动为零。
- token、模型费用及人工分钟累计全部子卡、尝试、任务编写与审查；父任务墙钟时间取统一起点到完成或截止的实际间隔，含排队与重试，不能把并行子卡时长之和叫墙钟时间。另列人工介入次数和累计执行时长。
- 子卡和单张工单层面的数据只用于定位问题发生在哪个阶段，不作为结论。

为什么必须这样：同一需求拆成十张卡，九张干净、一张含无关重构，按卡是 10%，按需求是 1/1。两组拆法不同时，按卡统计会显示「改善」，而用户收到的最终改动完全一样。

最小台账：`parent_id / scene / arm / base_sha / child_id / attempt_id / contract_hash / candidate_head / outcome / started_at / cutoff_at / usage / human_minutes / evidence_path`。父任务映射在派工前建立；历史映射无法确认则标未知，不按名称猜配对。两组在各自隔离工作区，从相同基线开始；父任务全部子卡就绪后还须在合成 HEAD 上跑整体验收，单卡 ready 不等于父任务 ready。

### 6.2 六目标指标表

数据来源成本：**免费**（决策日志、运行记录、Git 历史）、**低**（开发集加盲评）、**高**（预注册对照）。

| 目标 | 指标 | 定义（单位：父任务） | 来源 | 现有基线（实测，按工单，仅供量级参考） | 门槛（代定） |
| --- | --- | --- | --- | --- | --- |
| 质量 | 合格交付率 | 已 ready、通过隐藏参考验收测试、且盲评未发现缺陷的父任务 ÷ 全部父任务（判据见表后「合格的判据」） | 高 | 无 | 配对非劣效，口径见 §6.7 |
| 质量 | 错误放行次数 | 确认有问题的交付被放行 | 红队、对照、日常 | 无 | 0 |

**合格的判据**（v5.2 新增）：大任务的 diff 可达数百行，单真人盲评判断「功能完整」不可靠。B1 构造每个父任务时附带一组不向执行者展示的参考验收测试，在最终合成 HEAD 上运行，作为功能合格的主判据；盲评负责判断无关改动和测试覆盖不到的缺陷。无法构造参考测试的任务标为「仅盲评判定」，在报告中分列，不与有参考测试的任务合并出结论。

**合并后返工没有对照**（v5.2 更正）：§6.6 的结果取样不要求真实合并，只有 P6 有真实合并，而 P6 没有对照组。所以合并后返工率只作 P6 的描述性结果，不能支撑「相对对照减少」的声称；过程内的实际重做次数仍在 B4 两组间比较。

**缺失结果守护**：M2 是有最终 diff 时的条件比例，不能单凭它判定改善。无最终 diff 的父任务仍进入 N 和成本，另报中途 diff；不得标成干净。令 K 为最终 diff 无法判定的父任务数，另报告 U/N 到 (U+K)/N 的缺失结果界限。若组间缺失足以解释 M2 的下降，则结论为证据不足；即使完成率满足 §6.7 的非劣效界值，也不能跳过此判断。按场景、parent_id 配对；两组都有可评最终 diff 的父任务进入主配对检验，记录“仅对照有无关改动”和“仅实验有无关改动”的对数，采用双侧精确 McNemar 检验，显著性水平代定为双侧 5%（D-12，B4 前冻结）。两个场景分别检验、不合并；两个场景都达成才算完成，所以不做多重性调整。逐组 U/D 作为描述值。对全部 N 对进行最不利补全：实验组缺失按有无关改动，对照组缺失按无无关改动；保留已观察值。若补全后实验组发生率未严格低于对照，缺失即可解释改善，结论为证据不足；通过此方向检查仍须满足主检验和三项守护。脚本验收例：10 对中 8 对可双侧评分，仅其中 1 对为对照有、实验无；余下 2 对均为对照无、实验缺失。观察比例看似下降，最不利补全后实验为 2/10、对照为 1/10，必须判证据不足。合格交付为 0 时单位成本为不可计算，报告总投入及 0 次交付；usage 缺失标未知并报告覆盖率，不按 0 填补。

**最不利补全对缺失率很敏感**（v5.4 新增）：它要求「实验组无关改动数 + 实验组缺失数」严格小于「对照组无关改动数（缺失按无）」。实验组有三成父任务拿不到最终 diff 时，对照组的无关改动率必须高于 30% 才能通过；开发集的完成率只有 12/18。所以预期缺失率必须进入 §6.7 的可行性门。

**代定 D-11（待负责人确认；未确认前按上面的最不利补全作硬门）**：硬门改为「实验组缺失按对照组观察到的无关改动率的 95% 区间上界补全，对照组缺失按无」；全部按有无关改动的最不利补全保留为必报的敏感性结果，两者结论不一致时在结论里写明。这比 v5.3 宽松，是否接受由负责人决定。

**事件原因、实际重做和任务终态分开报告**。规则名只作筛查提示，不能自动断定 Worker 有错或无错：

| 类别 | 含义 | 判定 |
| --- | --- | --- |
| `effective_interception` | 被拒行为确实违反已批准授权或交付条件 | 对照冻结合同、操作目标和前后 diff；`ready.red-missing` 可能是正确拦截；测试出现在 `tests` 中不表示有写权限 |
| `friction` | 必要且合法的动作被错误合同或流程阻塞 | 核验原需求、必须修改的文件和拒绝证据；不能把所有 `plan.recorded` 或测试路径拒绝直接归入此类 |
| `environment_failure` | 依赖、工具或基础设施故障 | 环境日志支持；单列且计入成本，不一概归责 Worker |
| `expected_red` | 先红后绿预期失败 | 测试确因目标缺陷失败，不是依赖缺失；计入成本，不计返工 |
| `actual_rework` | 已有工作因缺陷或不必要改动被纠正 | 用前后提交、退回原因和修正内容核验；拒绝后正常继续开发不算，重投或放弃本身也不算 |
| 任务终态 | succeeded / failed / blocked / abandoned / not_started | 与事件分类分开；重投是 attempt，不增加父任务分母；原因不明标 unknown |

旧脚本的 6/12/4 是规则名启发式初分，保留为候选案例索引，不作已核实的误拦或返工基线。同一次拒绝可能引发一轮实际重做，两者分列，不相加成“总故障数”。

**效率的两级声称**：

- 「成本可接受」：每个合格交付的耗时和 token 相对对照劣化不超过 20%，且不超过 PREREG §5 上限。这只是容忍度，**不能说成效率提高**。
- 「效率提高」：正式运行前从每个合格交付的墙钟时间、token、人工分钟中指定一项主指标；其配对置信区间支持改善，其余不劣化。不能看完三项后挑最好的一项作主结论；探索性结果单列。

**返工窗口分别标注**：专项的合并后返工窗口为 14 天（代定）；Q1 的 T23 观察窗口是 7 天（已冻结）。两者不合并、不互相比较。

引用原 PR、修改同文件只是返工候选检索条件，还须核对原因；通过 issue 关联、回滚和人工回访补查遗漏。未满窗口的交付标为观察未满，未合并标为无合并后观察资格，不能算“零返工”。正式 B4 的配对单位、样本量、置信区间方法、缺失处理、停止规则及两个场景的检验安排在开跑前冻结；样本不足以证明非劣效时写证据不足，不按点估计放行。

### 6.3 审查退回与逐块归属

**现有入口（源码确认，真实交接未验证）**：g1-exp 的 Super Agent `cd384e7` 工作树干净。`src/sources/github.ts:190-194,424-425` 采集评论并 receive；`github-trigger.ts:48-76` 带文件、行号及末三行 diff 上下文；`core/intake.ts:19-59` 经来源过滤和线程订阅匹配写 Ticket input；`core/tickets.ts:234-269` 投递或在权限仍有效时恢复任务；`executor/dsh.ts:397-410` 将 input 以 `steer` 发到 `workerSessionId(ticket.id)`；`app/sessions.ts:164-168` 转入 agentDelivery。知识库源码指纹检查 45 MATCH、0 DRIFT/MISSING/ERROR；这份实例源码另行逐段核对，不把知识库指纹套给实例。

边界：未开启评论观察或被来源过滤时不会到 Worker；未绑定该 PR 的 Ticket 不保证回到原任务。人工停止的任务不能自动恢复；已结束任务只由系统认定的人类输入、且原授权复核通过时恢复，机器人或 Agent 自发评论不能保证唤醒。行号和末三行片段只是定位线索，审查须读取绑定 HEAD 的完整 diff。源码证明传递路径存在，未证明 Worker 会正确纠偏或自动触发最终复审。

**先做一条真实交接，再谈逐块归属**（开发集）：

1. 先确认运行中的 SA 进程加载的制品 SHA，与本节核对过的源码 `cd384e7` 不一致则先重新核对链路。在隔离开发任务上核对 PR 订阅、评论来源身份和 Worker 状态；审查者在 PR 上用行内评论指出一处无关改动，记录 base、候选 HEAD 和 comment ID。
2. Worker 删除该处改动，保留必要的配套修改，重新通过检查。
3. 审查者对最终 HEAD 复核。记录 trigger → Ticket input → Worker session → 修正提交 → 新检查 → 最终复审的关联证据；HEAD 再变则本次复审失效。
4. 记录：这次交接是否走通、额外 token、审查者耗时、实际纠正了几处、有没有误伤必要改动。

**交接试验的通过标准**（D-13 代定，试验前冻结）：至少做 3 次交接，其中 1 次故意给一条不应执行的评论（所指改动其实是验收项必需的），用来测 Worker 会不会盲从。判为走通须同时满足：3 次的关联证据链完整；2 次真实退回都删掉了无关改动且没有误伤必要改动；诱导评论那次 Worker 保留了必要改动并说明理由，或报 blocked。任一不满足记为未走通，逐块归属不开始。

**逐块归属声明保持为试验**，在上面的交接走通之后再做：

- 插件用 `git diff -U0` 机械列出改动块；Worker 为每一块填对应的验收项和一句因果说明；插件只查有没有漏填。
- 归属记录绑定基线提交和候选 HEAD。HEAD 变了，旧记录作废，因为同一块改动的行号和内容会变。
- 每个任务记录额外 token、审查时间、实际纠正数。
- 填齐理由只能证明填过。在证明它让审查更快或纠正更多之前，不进入正式对照的实验组，也不启用。大任务上它可能是最贵的一步，成本超标就放弃。
- **取舍门槛事前写定**（D-13 代定，试验前冻结，看到数据后不调）：与不带归属声明的同批任务相比，审查者耗时中位数减少至少 20%，或实际纠正的无关改动数更多；并且每个父任务的额外 token 不超过 20%。两条都满足才算有收益，否则放弃。

### 6.4 证据分三级投入与止损

| 级别 | 内容 | 成本 |
| --- | --- | --- |
| T0 遥测 | 决策日志、运行记录、Git 历史出全部免费指标 | 接近零 |
| T1 基线探查 | 每个场景用对照配置跑开发任务并盲评 | 低 |
| T2 预注册对照 | 冻结两组差异、门槛、样本量后正式对照 | 高 |

**止损规则只决定是否继续花钱**（开跑前冻结；下称「6/12 计数规则」，它是计数规则而不是一条 15% 的阈值，15% 只是停止与继续概率大致各半的位置）：

1. 第一段 6 个父任务：含无关改动的为 0 个则停止本批付费扩样；2 个及以上则进入 T2；恰好 1 个则加跑 6 个。
2. 合计 12 个：2 个及以上进入 T2，否则停止本批付费扩样。

这里的 6/12 是事前选定的不同父需求，不是同一需求反复重跑。下面的概率表假设各任务独立，同一模块的任务会相关，所以每个场景的探查任务里同一模块最多 2 个（D-14 代定）。

**计数用的标注须经真人复核**（v5.4 新增，D-14 代定）：附录 A 允许探查阶段用两份 AI 标注，但计数规则直接决定是否花 B4 的钱。所以进入计数之前，所有被标为「有无关改动」的父任务，以及至少 3 个被标为「无」的父任务，由真人复核；复核改判的以真人为准并留档。大改动的判定标准先按附录 A 校准。探查若有最终 diff 未产生或盲评缺失，不能把缺失填为“无无关改动”；该场景暂停作可评估性诊断并保持待交付，不能套用下面完整观测的二项概率宣称低基线。即使达到计数线，仍须完成 B4 预注册与预算门才能进入正式对照。

**预算在探查中途用尽**（v5.2 新增）：已完成的父任务数不足以按上面两步判定时，按缺失结果处理：该场景暂停、保持待交付，留档已完成的分子和分母；不得用已完成的部分套计数规则，也不得自行追加额度。

规则在不同真实发生率下的表现（二项分布精确计算，假设各次独立）：

| 真实发生率 | 停止扩样的概率 | 进入正式对照的概率 |
| --- | --- | --- |
| 5% | 91% | 9% |
| 10% | 72% | 28% |
| 15% | 53% | 47% |
| 20% | 37% | 63% |
| 30% | 15% | 85% |
| 40% | 6% | 95% |

真实发生率 20% 时仍有约 37% 的概率停止。所以**这个探查只够用来控制预算，支撑不了「该场景不需要改善」的判断**。

停止扩样时：

- 该场景的目标状态记为**待交付（证据不足）**，不是「关闭」，也不是「未观察到问题」。
- 留档：基线的分子和分母、任务清单及其代表性说明（规模、模块跨度、是否来自真实历史需求）。
- 重启条件（满足任一即可重新申请预算）：日常使用或审查中出现该场景的无关重构案例；有了更有代表性的任务来源；负责人决定加任务数。

计数规则以 15% 为分界的来由（量级估算，未配对两比例近似，双侧 5%、功效 80%）：基线 40% 降到 15% 每组约需 46 次运行，30% 到 10% 约 59，20% 到 5% 约 73，15% 到 5% 约 137。基线越低，证明改善所需样本越多。

| 逐块归属声明 | 无 | 仅当 6.3 的试验证明有收益时加入 |
| 人工审查 | 主结果取样之前两组都没有人工审查介入 | 相同 |
| 主结果取样点 | 父任务整体验收完成或统一截止时冻结候选 HEAD，取原始 base 至该 HEAD 的完整 diff；在人工纠偏前盲评 | 相同；子卡先本地合成，完整集成检查不能省略 |

补充规则：

- 两组的任务卡由同一人在开跑前写好并冻结；负责人抽查两组卡片的业务目标是否等价。
- 实验组的任务卡写作和拆卡所花的人工时间计入实验组成本。
- 对照组的编写、检查及必要合同修正时间也计入成本。对照是“可运行的现行 v3 写法”，不能推断成相对无任务卡系统或原生 DSH 的收益。
- 盲评包仅含相同原需求、base、最终 diff 和统一验收证据，隐藏组别、子卡数及归属解释；执行者不看参考修复。按父需求随机安排两组运行先后并记录资源占用，避免固定顺序及并发争用偏差。
- 专项执行表在开跑前填实际 plugin/SA/DSH 版本、实例、配置、模型、任务及提示词标识与哈希，禁止用“最新版本”。结果取样不要求真实合并 PR，也不授权自动合并；P6 的合并后观察以真实合并为起点。
- 「硬预算」「增量反馈」「逐块归属」三行在 B2 结束后填成确定的「有」或「无」，然后整表冻结。
- 审查退回的效果不在这次对照里测，它在 B2 单独做可行性试验。
- **拆卡带来的混杂须披露**（v5.4 新增）：对照组的大任务不拆卡，更容易撞上每父任务 60 分钟或 300 万 token 的停止线而没有最终 diff。报告里分组列出因停止线终止的父任务数；完成率和缺失率的组间差异可能来自拆卡本身，结论只能说整包效果，不能归因于合同写法。

### 6.7 守护指标的统计口径与可行性门（v5.2 新增）

**问题**：v5.1 要求合格交付率、完成率、干净合格交付率三项都「相对对照非劣效 −5pp」，又规定证明不了就写证据不足。按未配对两比例、单侧 2.5%、功效 80% 估算，基线 80% 时每组约需 1005 个父任务，90% 时约 565 个；而 §6.4 给出的 B4 量级是每组 46 到 137。照原口径，两个场景在结构上只能落在「待交付」，且要到 B4 花完钱才会暴露。

**设计更正（不改变严格程度）**：§6.6 本来就是同一父需求两组各跑一次，守护指标和 M2 一律按**配对**分析：守护指标用配对比例差及其置信区间，M2 的主检验与缺失补全按 §6.2 执行。未配对公式不再用于 B4 的样本量。

**界值是负责人的决定**。配对设计下所需的父任务对数取决于不一致对比例 ψ（两组结果不同的父任务占比）和界值 δ。下表按两组真实无差异、单侧 2.5%、功效 80% 的正态近似 n ≈ 7.85·ψ/δ² 计算，只说明量级：

| 不一致对比例 ψ | δ = −5pp | δ = −10pp | δ = −15pp |
| --- | --- | --- | --- |
| 10% | 314 | 79 | 35 |
| 20% | 628 | 157 | 70 |
| 30% | 942 | 236 | 105 |

单侧 5% 时约为上表的 0.79 倍。ψ 目前没有实测值。

**代定 D-8（待负责人确认）**：配对分析；界值 −10pp；单侧 2.5%。在表中 ψ=10%–30% 的假设下，−5pp 约需 314–942 对；−15pp 意味着可以容忍七分之一的交付变差，作为守护偏松。−10pp 仍然需要每场景约 80 到 240 对，是否可行由下面的门来判断。

**可行性门**（在花 B4 的钱之前回答「能不能证明」）：

1. B1 冻结 B2/B3 各自独立的任务清单和 B4 入选规则，正式任务数留到 B2 后估算。分别对三个守护指标计算不一致率 ψ。优先用开发阶段可用的配对数据报告不一致对数、总对数及区间；样本稀少时用区间上端做敏感性分析。只有边际成功率 p₁、p₂ 时，理论上界为 min(p₁+p₂, 2−p₁−p₂)；若边际也是估计值，列出其合理范围并重算。独立假设仅作为一个情景。例如两组成功率均为 80%，独立时 ψ=32%，可能上界为 40%；δ=10pp 时按上式向上取整分别需 252、314 对。
2. 两个场景分别估样。三个守护指标逐项估算，M2 按预期改善和两方向不一致对概率评估配对检验功效。各项所需任务数的最大值只是起点；预注册时评估联合达标的功效和缺失配对造成的损耗，写明最终任务数依据。B3 只跑对照组，用于更新成本及对照端可评估率，不能据此估计两组配对 ψ。B3 后、B4 首次运行前，由负责人确认 D-8、正式样本量与预算，再冻结正式清单和分析规则。
3. 复算后所需对数超出可构造的任务数或负责人批准的预算时，只有三条出路，都须在看到 B4 数据前由负责人选定并写进预注册：放宽界值；缩小为单一场景先做；或不开 B4，该场景直接记「待交付（证据不足）」。不允许带着一个已知证明不了的门槛开跑。
4. 界值、单双侧、配对方法和任务数冻结后不调。结论措辞跟随实际冻结的界值，例如「在 −10pp 界值下非劣效」，不得简写为「质量不下降」。

Q1 的 −5pp 属于 PREREG v1.3 的锁定口径，不受本节影响。Q4（附录 A）的完成率非劣效存在同样的样本量问题，在其预注册时按本节的方法单独过一次可行性门。

### 6.8 验收结构、样本量重估与可行性门的补充（v5.4 新增，均为代定、待确认）

**主指标和守护指标的样本量不在一个量级。** M2 配对检验的功效（双侧 5% 精确 McNemar；假设两组独立、无缺失；只说明量级）：

| 对照组无关改动率 → 实验组 | 父任务对数 | 功效 |
| --- | --- | --- |
| 40% → 15% | 60 | 82% |
| 30% → 10% | 80 | 85% |
| 20% → 5% | 100 | 88% |

也就是 M2 需要 60 到 100 对；而 §6.7 算出守护指标在 −10pp 下要 252 到 314 对（两组成功率 80% 的情景），是主指标的 3 到 4 倍。B4 的规模实际由守护指标决定。

**代定 D-10：守护指标只留一个硬门。** 三项守护是嵌套的（干净且合格 ⊆ 合格 ⊆ 完成），高度相关。代定为：

- 合格交付率保留为配对非劣效的硬门，界值按 D-8。
- 完成率和干净且合格交付率改为必报项：报告配对差和 95% 区间，要求「未证明劣化」，即区间没有整体落在界值以下。
- 这样做去掉了三项同时达标带来的功效损失，但**不降低单项硬门所需的对数**；对数能否降到可执行的范围，取决于实测的不一致率，见下面的重估。
- D-10 放宽了 v5.3 的验收定义。负责人未确认前，§7.1 仍按三项都非劣效执行。

**代定 D-12：不一致率用盲态样本量重估来取得。** v5.3 说优先用开发阶段的配对数据，但 B2 是机制试验、B3 只跑对照组，没有任何阶段让两组跑同一批任务。单独做小规模配对试跑也估不准：20 对里观察到 4 对不一致时，95% 区间是 8% 到 42%。代定为：

1. 预注册时按 §6.7 的情景给出初始对数和负责人批准的对数上限。
2. 每个场景跑完 40 对时做一次重估。脚本只输出各守护指标「两组结果不一致」的总对数，不输出方向，也不输出任何一组的成功率。
3. 用不一致率的点估计重算所需对数，区间上界另算一次作敏感性。所需对数只能上调，且不超过上限。
4. 重算结果超过上限时，按事前写好的规则停止该场景并记「待交付（证据不足）」，不得看过方向后再决定。
5. 另设一个期中检查点，在最终对数的 50% 处，只用于附录 A 的「已证明劣化」暂停，不做提前宣布有效。

**可行性门增加两项约束**（与 §6.7 第 3 步的三条出路共用）：

- **缺失率**：用 B2、B3 实测的「无最终 diff」比例，按 §6.2 实际生效的补全口径（最不利补全或 D-11）先算一遍，在预期的 M2 改善幅度下能否通过。算不过就不开 B4。
- **任务构造能力**：两个场景各要开发集、12 个探查任务和正式任务，每个都要参考修复、隐藏参考验收测试和两套任务卡，大任务还要多里程碑。B1 估出单个任务的构造工时，并清点 Dubbo 训练截止后的可用修复数；所需对数超出能构造的数量时，同样按三条出路处理。
